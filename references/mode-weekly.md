# 模式 C：每周工作周报（MODE=weekly）

触发：自动化 C，每天 17:20 **先判定星期**，仅周五继续；非周五自动结束（见下）。
目标：产出本周"干了什么 + 没干什么"的**两层周报**，分别存入 ③ 自阅周报 与 ④ 领导周报 两个独立文件。

## 0. 星期网关（由自动化 C 的 prompt 保证，这里再强调）

触发时先判定当前星期：
- 主：`date +%u`（本地系统时间，1=周一..7=周日，**周五=5**）。受控机器上可靠、零依赖、零延迟。
- 可选交叉校验：如担心系统时间被篡改，可 `curl --max-time 6` 调 `https://worldtimeapi.org/api/timezone/Asia/Shanghai` 解析 `day_of_week`（0=周日..6=周六，周五=5）做二次确认；**本环境该 API 常不可达，抓取失败时以本地 `date` 为准，不阻塞、不重试**。
- 判定：周五 → 继续；否则输出"今日非周五，跳过周报"并结束，**不写文件**。

> 本模式只在周五被真正执行；非周五时自动化已提前结束，不会进入本流程。

## 1. 抓取本周会话并富化上下文

- 时间窗：本周一 00:00 至周五 17:20（本地日期，UTC 换算）。
- **主源**：`sessions` 表，按 created_at/updated_at 过滤本周，读取完整元数据（含 `custom_title`、`cwd`、`project_id`、`model`）。`custom_title` 是用户手动设置的标题，比自动 title 更准确。
- **trace 回溯**：本周 `<DATA_ROOT>/daily/YYYY-MM-DD.md` 的"大总结"节是周报主干输入。若某条日志内容模糊（如"制定XX方案"未说明具体方案内容），使用 `read_trace.py --session <session_id>` 回溯该会话的实际 trace 数据，提取用户原始提问和 AI 产出，补充具体上下文。
- **待办交叉引用**：读 `<DATA_ROOT>/todos.json`，提取本周完成/更新的待办 `result`/`notes` 字段，与 daily 日志交叉验证，确保"没干什么"基于真实待办差距。
- **不再依赖 `conversation_search`**（持续返回 0 结果）。
- **辅助材料**：本周 `daily/YYYY-MM-DD.md` 的"大总结"节。"大总结"中的每条事项在写入时已有 trace 上下文支撑，周报可直接引用其具体内容。

## 2. ③ 自阅周报（weekly-self，大总结）

- 内容：分两大部分书写——「第一部分：本周概要」汇总各板块简要说明（每条遵循「三要素」点名规则，见下方模板）；「第二部分：Trace 回溯原始数据」按板块列出 trace 数据，供核对简要说明的准确性。末尾附"本周没干什么"。
- 落盘：`<DATA_ROOT>/weekly-self/YYYY-Www.md`（如 `2026-W28.md`）。若同周文件已存在，追加而非覆盖。

## 3. ④ 领导周报（weekly-lead，小总结，对③再压缩）

- 定位：可单独转发/归档的领导成品，与 ③ 分离存储。落盘：`<DATA_ROOT>/weekly-lead/YYYY-Www.md`（同周编号）。若已存在，追加而非覆盖。
- 文风遵循用户提供的 `style-samples.md`（若有），否则通用规范（两段式、编号、单行单产出、协作方按 ⑤ 规则点名）。
- **④ 目标格式（2026-08-07 用户确认）**：**短标题（固定简称库）+ 单行式**——每条 `N. 标题：<里程碑串>，<结果>`，整行 ≤50 字（不含编号），领导一眼扫完。
- **标题简称库（固定映射；新板块须用户确认后补入，AI 不擅自创造）**——**以下为本项目实例，各团队使用时应替换为自己项目的简称映射（机制相同：简称 ≤6 字，→ 后为项目全称）**：
  - 生活服务APP → 启航&中旅生活服务移动端平台（第一阶段）
  - 昭津系统重构 → 昭津智能物流系统改造升级项目
  - 用友企微审批 → 企微审批页面设计（UI 审核）
  - 系统运维 → MDG 客商 / 共享节点 / 银行账户等运维类事项
  - AI舆情监测 → 启航1331 舆情采集项目
  - 智能排班微服务 → 智能排班微服务能力中台研发及 AI 推理增强项目
  - 设备管理 → 办公设备采购/登记/报销
  - 工作任务平台 → 数字化办公平台 / 工作任务平台
  - 新板块出现时：AI 从 daily 日志高频术语提取 ≤6 字短标题，**经用户确认后补入本库**。
- **③→④ 提取管线**：
  1. 读 ③「第一部分：本周概要」各板块「三要素」内容。
  2. **标题选取**（重写规则）：命中上方**简称库**；未命中新板块按上规则提议短标题。**禁止使用长项目全称作标题**（如"XX平台建设项目（第一阶段）"）。
  3. **单行式蒸馏**（重写规则）：每条**严格一行**，格式 `标题：<里程碑串>，<结果>`。里程碑用 `→` 连接，只列关键节点（≤3 个），如「报价分→评审会→评委签字」；结果写实际产出（如「供应商选定请示上OA」），**不写预测性"待XX"**（预测归入下周计划）。
     - 状态词仅用两级——**完成**（done + 有产出）或**推进中**（有进展但未完）。本周总结去掉"持续/正在/进行"三个模糊状态词；**下周计划的例行延续事项可用"持续推进"**（用户手笔认可，如"持续推进MDG和BIP系统日常数据运维"）。完全 done 的条目不加百分比；推进中事项可标 `完成进度约N%` 或写 `推进中`（不确定时用后者）。
     - **删除细节**：报价金额、响应文件大小、评审组名单、具体工具/脚本名、调色盘等过程性细节一律不写，只留里程碑与结果。
  4. **板块取舍规则**：领导周报**只列有实质业务产出的核心板块**（本周 3~5 条）；AI 写作工具链、待办体系等内部事项不进入呈报。**有系统名的例行运维可进入呈报**（如"MDG和BIP系统日常数据运维"——领导关心核心系统，用户手笔认可）。下周计划同样 3~5 条。
  5. **下周计划**：措辞必须**直接引用 daily 日志或 todos.json 原文**，禁止自行概括关键术语。从 `todos.json` 的 open/waiting 项 + ③「本周没干什么」中带 due 日期的项提取，压 3~5 条，领导口吻写下一步。**同板块软约束（2026-08-26 补）**：同一短标题板块下周计划 ≤2 条；超出时合并同类项或只取更关键一条（避免同一板块刷屏，如"设备管理"连续 2 条）。
  6. 领导口吻：主动态、无"我"、无过程细节、禁编造；不超出 ③ 信息范围。
  7. **复核步骤**：生成后复核 ① 标题全部命中简称库 ② 每条整行 ≤50 字 ③ 无模糊状态词 ④ 计划措辞每个名词/动词都来自原始数据，非 AI 杜撰。
- **领导周报写作原则（通用 7 条，2026-08-07 用户定稿提炼）**——从"AI 拟稿 vs 用户手写定稿"逐条对比中提炼，**与上方提取管线冲突时以本原则为准**：
  1. **如实标注阶段与角色**：写"初稿/基本定稿/日常"如实阶段；"协助撰写/协助开展"如实角色；不夸大完成度，协助事项不写"完成"。
     - ✗ 完成XX方案终稿并校验通过　✓ 协助撰写XX方案初稿
  2. **本周总结只写已完成事实，不写预测**："待XX""预计XX"等未发生事项不写入本周总结（放下周计划）。
     - ✗ 供应商请示已上OA，待系统定标　✓ 供应商选定请示上OA
  3. **量化工作量语言**：用"N次研讨/N轮修改"让领导感知工作量，替代内部编号、字段名、术语。
     - ✗ 完成v3审核三连改（财务6条并入/交互一致性）　✓ 与供应商进行2次研讨，完成4轮UI修改，基本定稿
  4. **点系统名，不点内部文件/编号**：保留 MDG/BIP/crawl4ai 等系统或工具名；不写模板文件名、单证编号、数据条数、预算金额、校验过程。
     - ✗ 完成客商导出4条并生成MDG013模板，1条待核　✓ MDG和BIP系统日常数据运维
  5. **不写等待/被动事项**："等XX回复""等待XX提供信息"不进入周报；只写自己可控的行动。
     - ✗ 等待XX提供6家公司支行信息　✓ 持续推进XX系统日常数据运维
  6. **每条一个核心动作**：删次要并列项（如"注册apple/google开发者账户"）、删"思考"类意向；只留最核心一个动作。
     - ✗ 购买XX资产；跟进库存不足问题（等回复）　✓ 购买XX资产增值服务
  7. **里程碑箭头串 ≤3 节点**：关键过程用 → 连接，只列领导可感知的里程碑。
     - ✓ 报价分→评审会→评委签字

## 输出格式

### ③ weekly-self/YYYY-Www.md
内容分两大部分：「第一部分：本周概要」汇总各板块简要说明；「第二部分：Trace 回溯原始数据」按板块列出 trace 数据，供核对简要说明的准确性。末尾附"本周没干什么"。

```
# 2026-W28 周报（周一 ~ 周五）· 自阅

## 第一部分：本周概要
### 一、<项目板块>
<简要说明 1~2 句话>。写作须遵循「三要素」强制点名：每条都要写出【具体对象 —— 供应商名 / 系统名 / 合同文件名 / 智能体模块名 / 具体文件】+ 具体动作 + 产出结果。例：「某乙方(供应商)的 XX 总包合同 + YY 协议：完成甲方视角审核，N 条拍板结论用 redline 直接改供应商文件」。严禁只写动作不写对象的笼统写法（如"完成采购文件审核""完成 AI 智能体梳理""完成某系统管理"）。

## 第二部分：Trace 回溯原始数据（仅供核对）
### 一、<项目板块>
<按会话逐条列出用户原始提问与 AI 产出摘要>

## 本周没干什么（遗留/阻塞）
- <计划未推进的事项 + 原因>
```

### ④ weekly-lead/YYYY-Www.md
```
# 2026-Wxx 周报（周一 ~ 周五）· 呈报

## 一、本周工作总结
1. <短标题（命中简称库）>：<里程碑1→里程碑2→里程碑3>，<结果/卡点>。
2. <短标题>：<里程碑串>，<结果>。
（3~5 条，每条整行 ≤50 字。状态词两级：完成/推进中；未完成事项点出卡点）

## 二、下周工作计划
1. <短标题>：<下一步动作（措辞直接引用 todos.json 原文术语）>。
2. <短标题>：<下一步动作>。
（3~5 条，源自 todos.json + ③遗留带 due 项）
```

示例（通用化写法；真实完整样本见用户数据根 `<DATA_ROOT>/style-samples.md`）：
```
1. XX平台：完成招标全流程（报价分→评审会→评委签字），供应商选定请示上OA。
2. YY系统重构：协助撰写采购立项请示及采购文件初稿。
```

## 纪律

- 周报只在周五生成。
- 真实数据；"没干什么"基于待办/计划与实际的差距，不臆测。
- ③ 求全、④ 求简；④ 不得超出 ③ 信息范围。
- 简要说明「三要素」强制点名（**仅 ③**）：每个板块的概要每条都要写出涉及的具体供应商 / 系统 / 合同文件 / 智能体模块名称（适用于所有板块）。
- **④ 结构铁律**：必须含「一、本周工作总结」+「二、下周工作计划」两段；编号 `N. 短标题：` 严格一行一条，整行 ≤50 字；标题命中**简称库**（见上方 §3），项目全称不出现；**协作方点名规则**：乙方供应商（`todos.json` 中 `supplier` 字段非空）→通用化不点名；内部协作方/关联系统（`supplier` 为空）→可保留点名；**无"遗留"段**。
- 每周生成后提示用户：④ 已就绪、可转发。
